# Generated invocation-context executable checks

This test-only app exposes Runtime API and HTTP API v2 gateway correlation IDs
through `/api/identity`, then observes the same values in accepted `nextgo.After`
work. It is not a production debugging endpoint, authentication mechanism, tracing
exporter, AWS integration or a browser test. Serialized observations are public
fixture values.

The executable test requires **both** `deployment` and `invocation_context` build
tags. Ordinary `go test -tags=deployment ./tests/deployment` excludes it and keeps
its existing demo-binary interface. Missing inputs in the explicitly selected
identity fixture fail rather than skip. The ordinary Go CI matrix runs the seven
identity API unit groups; the dedicated workflow separately runs this generated
executable fixture.

On Linux with Bash, from the repository root with a supported Go SDK and no manually generated
fixture helpers, use four build/run commands:

```sh
work=$(mktemp -d)
go build -trimpath -buildvcs=false -o "$work/nextgo" ./cmd/nextgo
"$work/nextgo" build --out "$work/production" "$PWD/tests/deployment/fixtures/invocation-context"
go test -c -trimpath -buildvcs=false -tags=deployment,invocation_context -o "$work/invocation.test" ./tests/deployment
export NEXTGO_TEST_INVOCATION_BINARY="$work/production/server"
export NEXTGO_TEST_INVOCATION_BINARY_SHA256="$(sha256sum "$NEXTGO_TEST_INVOCATION_BINARY" | cut -d ' ' -f 1)"
export NEXTGO_TEST_UID="$(id -u)"
(cd / && "$work/invocation.test" -test.run='^TestInvocationIdentityGeneratedExecutable$' -test.v=true -test.timeout=90s)
```

Run as a nonroot user. The binary path must be absolute and executable and the
digest must be its actual lowercase 64-hex SHA-256. No application build occurs
in the test. The CLI build emits the four route/action helper files; preserve
those actual generated bytes when collecting evidence, and do not handwrite them.
The dedicated workflow checks that only those four source additions occurred.
No separate `generate --check` step is implied by these commands.

When collecting proof, capture the actual test exit status and complete verbose
output with Bash `pipefail`, then call `bash tests/deployment/fixtures/invocation-context/verify-output.sh LOG
PROOF_DIRECTORY ACTUAL_EXIT_CODE`. It requires one top-level PASS, exactly three HTTP/buffered/
streaming mode PASSes, nine exact paired response/After identity observations,
three actual child-Wait exit-0/no-KILL/controller-join receipts and no skips or
empty selection. A successful exit with “no tests to run” cannot qualify.

Each mode starts a fresh generated executable outside the checkout and issues
three requests in that process. Runtime IDs differ from gateway IDs; the third
event omits the gateway ID, while an actual retained first request context keeps
its first IDs. Buffered and streaming checks inspect real Runtime API publication
traffic and accepted After/next-poll ordering. Native HTTP has empty IDs and does
not claim that After certifies client delivery. One Go loopback controller handles
the mock Runtime API and callbacks; no Node/Python gateway or global environment
mutation is used.

The workflow is a Linux AMD64, nonroot functional check with source-independent
working directories. It does not certify Docker read-only isolation, Linux ARM64,
resource/soak bounds, final process-namespace sampling, real Lambda/AWS behavior,
cloud credentials, tracing conversion or a full release gate. Its pinned SDK
matrix is Go 1.24.13 and 1.27.3. JavaScript, Node and Python are not required by
this fixture. No execution result is conferred by merely adding the workflow.
