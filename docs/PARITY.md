# Next.go capability parity and production release gates

Research baseline: **October 23, 2026**, official Next.js documentation identifying **v16.4.3** as latest ([release](https://github.com/vercel/next.js/releases/tag/v16.4.3), commit `29bbeab09981148ade186e8599ecdede15abc281`). The original October 22 inventory used v16.4.2; the patch delta is recorded below without removing any capability or gate. The [official latest-release API](https://api.github.com/repos/vercel/next.js/releases/latest) was rechecked on October 24 and still identifies stable v16.4.3. This is a capability inventory and an unfinished release checklist. **Next.go is not currently feature-parity or production-mature.** Passing the existing sample tests proves the smaller Go/WASM vertical slice; it does not establish the claims in this document.

The target is an alternative implemented in Go, with Go/WASM browser behavior and only the JavaScript runtime bridge that WASM requires. Equivalent user-visible capabilities may have idiomatic Go APIs. React, JSX, RSC wire formats, JavaScript configuration syntax, npm packages, and exact Next.js source APIs are not compatibility promises. Their underlying capabilities remain in this inventory. An existing Next.js application cannot currently be imported or run unchanged.

The baseline includes the current App Router, supported Pages Router application capabilities, documented opt-in features, deployment behavior, and developer experience. App Router is the current recommended router, while Pages Router remains supported. A second Go router syntax is not necessary to offer equivalent SSR, static generation, data-loading, API, and navigation capabilities. [App Router](https://nextjs.org/docs/app), [Pages Router](https://nextjs.org/docs/pages), [Pages rendering/data capabilities](https://nextjs.org/docs/pages/building-your-application).

## Reading the status

- **Implemented**: source and focused tests exist for the limited behavior stated in the row. This does not mean production qualification.
- **Partial**: a usable subset exists, with the missing semantics stated explicitly.
- **Missing**: the inspected framework has no corresponding managed capability. An application being able to implement something manually using Go or browser APIs is not framework parity.
- **Unverified**: a production property requires measurements, deployment evidence, or broader tests that are not currently available.
- **Experimental baseline**: Next.js marks some capabilities experimental or unstable. They remain visible as separate parity work; an implementation must record support and limitations rather than silently treating them as stable requirements already satisfied.

## Ordered remaining work

This order establishes prerequisites; it does not reduce the final target. Ship runnable, tested milestones, retain this full inventory between them, and keep the goal open while missing capabilities or production gates remain.

1. **Contracts and conformance:** version the public Go APIs and internal navigation protocol; introduce typed application configuration and feature fixtures. Add baseline release records, cross-engine CI, fuzzing and performance measurements so new features have meaningful gates.

3. **Secure mutation foundation:** build on explicit bounded action/form handlers and origin validation; add generated typed calls, integrated pending/validation UX, one-response refreshed UI and durable retry guidance. Add a real authenticated sample and application-data authorization tests.
4. **Data lifecycle:** extend process-local TTL/data/page caches and invalidation with request memoization, byte limits, read-after-write and stale/error profiles. Add durable/shared adapters and multi-instance/browser/CDN conformance before claiming production caching.

9. **Production qualification:** run all G01–G11 gates against an immutable release candidate, publish benchmark/security/browser/deployment/recovery reports, fix failures, test upgrades and rollback, and only then publish a scoped evidence-backed parity/maturity claim.

### Keeping the comparison current

Before each release, recheck the official [getting-started index](https://nextjs.org/docs/app), [file conventions](https://nextjs.org/docs/app/api-reference/file-conventions), [functions](https://nextjs.org/docs/app/api-reference/functions), [guides](https://nextjs.org/docs/app/guides), and [configuration reference](https://nextjs.org/docs/app/api-reference/config/next-config-js). Add newly documented capabilities and mark experimental status explicitly. Changes in Next.js defaults, such as caching or prefetching, require semantic tests rather than renaming existing APIs. Keep the release comparison pinned to a named baseline so “parity” is a verifiable statement rather than an unbounded slogan.
